# ADR 001: Core Technology Stack and Asynchronous Worker Pattern

**Date:** 10 November 2026  
**Status:** Proposed (Pending Team Review)  

## Context
The FulfillOps capstone requires building an order-processing platform capable of handling highly concurrent API requests, ensuring cross-replica idempotency, and safely processing orders asynchronously. The system must never oversell inventory and must guarantee at-least-once job execution (with bounded retries and dead-letter queues) for background workers. 

We must choose a runtime, a durable data store, and a message-queueing architecture that satisfy these extreme reliability constraints without introducing unnecessary infrastructure overhead.

## Decision
We have decided to use the following technology stack:

1. **Language & Framework:** Python 3.11+ with FastAPI.
2. **Database:** PostgreSQL 16.
3. **Database Access:** SQLAlchemy 2.0 and Alembic.
4. **Queueing Strategy:** PostgreSQL Transactional Outbox Pattern (using a dedicated jobs table).

## Rationale (The "Why")

### 1. Python + FastAPI
The API contract is strict regarding JSON validation, required fields, and HTTP status codes (e.g., returning `422 INVALID_QUANTITY` or `400 INVALID_JSON`). FastAPI natively integrates with Pydantic for data validation. This allows us to define our request boundaries once and automatically enforce the 16 KiB payload limit, maximum 10 items rule, and precise data types without writing manual parser logic.

### 2. PostgreSQL 16 (Atomic Concurrency)
To pass the `--stress` checker and advanced grading gates, we must prevent overselling when clients request the same items simultaneously. PostgreSQL provides ACID guarantees. We will use row-level locking (`SELECT ... FOR UPDATE`) to atomically check and decrement inventory. Furthermore, unique constraints on the `Idempotency-Key` at the database level will inherently prevent cross-replica race conditions.

### 3. Transactional Outbox Pattern (Reliability)
Instead of introducing Redis Streams, we will use a "jobs" table inside PostgreSQL to manage the worker queue. 
* **The Dual-Write Problem:** If we used an external queue like Redis, the API could successfully commit the order to PostgreSQL but crash before sending the message to Redis, losing the job forever.
* **The Solution:** By using a Transactional Outbox, we write the accepted order AND the worker job into the database in the *exact same transaction*. If the transaction commits, the order is accepted and the job is guaranteed to be queued. This directly satisfies the rubric requirement for "exact-once business effect" and "durable at-least-once job processing."

## Consequences
* **Positive:** Reduced infrastructure complexity (we only have to deploy and monitor PostgreSQL, not Postgres + Redis). 
* **Positive:** Absolute guarantee of data consistency between the API layer and the worker queue.
* **Negative:** Workers will need to poll the PostgreSQL outbox table to claim jobs. While polling can create database load at massive scale, it is highly manageable and performant for the workload defined in this capstone.

## Compliance with Assignment Gates
* **WP1:** Establishes the architecture, domain model, and invariants.
* **Advanced Gate A:** Transactional outbox fulfills the durable at-least-once processing requirement.
* **Advanced Gate B:** Database-level uniqueness constraints will enforce the cross-replica idempotency requirement.
